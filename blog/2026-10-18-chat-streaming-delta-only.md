知远的对话由 Pi SDK 驱动。主进程接收 Pi 的事件，翻译成界面事件，经 IPC 发给渲染进程，渲染进程再写进 Redux 画成气泡。[PR #1127](https://github.com/rongxinzy/RongxinAI/pull/1127) 修了这条链路上的几个问题。这篇记录现象、原因、改法和验证方式。文中的数字都能用仓库里的回放夹具复现，方法见文末。

![聊天页流式管线修复前后对比](/blog-assets/2026-10-18-streaming-pipeline.svg)

## 现象

**全文反复重发。** 一段带工具调用的 GLM 对话，最终回答 1940 个字符。旧管线在流式过程中发出了 396 次 `content_patch`，其中 382 次从 offset 0 开始，也就是把当前全文重新发一遍。这一段对话的 IPC 总量约 696 KB，平均每个字符 359 字节。每次全文重发都带上当前全文，总量随回答长度近似平方增长，回答越长越明显。

**自动重试多出气泡。** 模型返回 503 这类可重试错误时，Pi 会自动重试。旧代码在每次重试的 `turn_start` 都新建回答消息：重试一次，界面上是两个回答气泡；重试两次，数据库里留下三条非空的回答记录。用户看到的是同一个问题被回答了几遍。

**工具结果卡住后续事件。** 较大的工具结果会被送进共享 worker 池提取展示文本。为了保证事件顺序，它后面的所有事件（包括正文 delta）都要等这一步完成。这个池同时服务产物收集，队列满时直接 reject，事件不带展示文本往下传，界面上的工具结果就是空的。

## 原因：快照跑在 delta 前面

Pi 的 agent loop 在每个流式事件上发 `message_update`，同时带两样东西：本次事件 `assistantMessageEvent`（含 `delta`）和当前消息快照 `message`。看 `@earendil-works/pi-agent-core` 1.3.0 的实现：

```js
case "text_start":
case "text_delta":
// ...
  partialMessage = event.partial;
  await emit({
    type: "message_update",
    assistantMessageEvent: event,
    message: { ...partialMessage },
  });
```

`message` 只是浅拷贝，`content` 数组和里面的块仍然是 provider 会继续改写的那个对象；`assistantMessageEvent.partial` 本身就是它。这带来两个后果：

1. 快照可能比 delta 走得更快。录下来的 GLM 对话里，`text_start` 事件本身没有 delta，但它的快照里已经有 `# Project` 这 9 个字符。
2. 事件被处理时，快照内容可能已经变了，读到的不一定是这一帧的状态。

旧的累积器在有快照时优先用快照替换整段文本（原注释的理由是“防止混合的思考块和正文块漏掉内容”），然后把结果和已经发给界面的文本比较。只要新文本不是旧文本的纯追加，就走兜底分支：关掉当前的流式片段，发一次全文快照，渲染进程收到的是 `content_patch`。快照和 delta 节奏对不上，这个兜底分支就从“偶尔恢复”变成了常态。

## 改法

### 1. 增量事件只用 delta

`text_*`、`thinking_*`、`toolcall_*` 这些增量事件一律不读快照：

```ts
if (event && this.eventUsesIncrementalOnly(event)) {
  return this.applyDeltaEvent(event);
}
```

`*_start` 开一个空段，`*_delta` 往后追加，`*_end` 用事件自带的 `content` 收尾。没有 delta 的旧式累积快照仍然兼容。`message_end` 对账前先深拷贝一份消息（`clonePiStreamMessage`），不保留对 SDK 可变对象的引用。

### 2. 重试复用同一个气泡

收到 `auto_retry_start`，或者 `agent_end` 带 `willRetry: true`，并且当前已经有回答或思考消息时，打上“重试复用”标记。下一个 `turn_start` 看到标记就沿用原来的消息 id，并发一次带 `metadata.streamReopen: true` 的 `message_update`。主进程的转发层和渲染进程都认这个标记：把消息从“已结束”集合里移出来，重新进入流式状态。

几个边界情况：

- 重试期间保留上一次的文字，新的 delta 到达之前不清空，也不冻结。
- 不可重试的错误（比如 401）立即收尾，清掉重试标记，不留一直“生成中”的气泡。
- 只删除从没显示过任何内容的空回答占位：数据库里没内容、流式过程中没发过内容、内存里也没有文字，三个条件都满足才删。思考消息不删。
- 删除时发 `message_removed` 通知界面。这里还踩了一个坑：渲染进程的事件校验 `isPiUiEvent` 一开始不认识这个类型，默认返回 `false`，删除事件被直接丢掉，界面上留下幽灵气泡。最后一个提交补上了这个分支。

### 3. 工具结果同步提取

事件投影队列不再异步。`tool_execution_end` 的展示文本在主线程上同步生成，规则和原来 worker 里的一致，另外跳过图片块，避免 base64 图片数据被当成文本。后续事件不用再排队等待，也不会因为池满拿到空结果。代价是这部分计算回到了主线程。

### 4. 上下文用量查询延后

以前每条回答消息结束时就排一次上下文用量查询。现在只记下待查的用量，等这次运行结束时再查；同一次运行里有多条回答时，后一条入队前先把前一条查掉。每条回答最多查一次，查询不再插在流式事件中间。

## 效果

同一份录制分别喂给修复前（`95a64f55`）和修复后的代码，走真实的 `PiRuntimeAdapter` → 转发层 → 渲染进程管线，存储用内存 SQLite。事件按每个 1 ms 推进，和 CI 里的回放测试一致。字节数是会话内所有 IPC 事件 JSON 序列化后的 UTF-8 长度，除以最终回答的字符数。

录制 A 带工具调用和思考，最终回答 1940 字符；录制 B 带思考和工具调用，最终回答 2676 字符。

| 指标 | A 修复前 | A 修复后 | B 修复前 | B 修复后 |
| --- | --- | --- | --- | --- |
| IPC 事件数 | 905 | 52 | 1371 | 65 |
| IPC 字节数 | 约 696 KB | 约 20 KB | 约 1.2 MB | 约 26 KB |
| 每字符字节数 | 359 | 10.3 | 450 | 9.7 |
| 流式中的 content_patch | 396 | 0 | 605 | 0 |
| 其中从 offset 0 全文重发 | 382 | 0 | 584 | 0 |

每字符的 IPC 开销降到原来的 1/35 到 1/46。按录制里的原始时间间隔回放，修复后是 7.2 和 6.0 B/字符，修复前的结果不变。

正确性方面：

- 每一帧界面上显示的文字都是最终文本的前缀，不重复，也不错位。
- PR 新增的回放和重试测试（3 个文件、23 个用例）放到修复前的代码上跑，10 个失败。其中重试一次出现两个回答气泡，重试两次数据库里留下三条回答记录。
- 修复后，单次重试、连续重试、重试立即失败、重试耗尽、不可重试的错误、用户中途停止，每个场景都有对应测试：只有一个回答气泡，数据库内容和界面一致，结束后没有残留的“生成中”状态。

## 验证方法

### 录制真实对话，在 CI 里回放

两段真实的 GLM 对话按行录成 JSONL，每行是一个原始 Pi 事件加时间戳。较大的一份用 gzip 存（约 25 KB），以通过仓库的大文件检查。`tests/streamingGlmReplay.test.ts` 把它们回放过整条管线，断言：

- 每一帧显示的文字都是最终文本的前缀；
- 最终显示和数据库里的内容都等于录制里 `message_end` 的正文；
- 结束后没有消息还标着“流式中”；
- 流式过程中的 `content_patch` 不超过 2 次；
- IPC 字节数除以回答长度小于 20。

这些测试在每个 PR 的 CI 里跑。

### 测试构造器默认“快照领先”

测试里用来拼 Pi 事件的 `PiTurnBuilder` 改成默认生成“快照比 delta 多一个字符”的事件，`*_start` 也可以带领先的快照。理想化的事件流以后需要显式关掉这个选项才能拿到。

### 变异测试：确认测试真的能抓到回归

`scripts/ci/run-streaming-mutations.py` 定义了 23 个单行“回滚”，每个对应一处修复，比如累积器重新读快照、重试不复用 id、不跳过图片块、转发层丢掉 `streamReopen`。脚本逐个打补丁，跑 11 个流式相关的测试文件，再还原，记录有没有测试失败。

在合并后的代码上重跑的结果：14 个变异被测试抓到，8 个没有，1 个因为代码已经改过、补丁锚点对不上而没有执行。没抓到的 8 个集中在重试标记的设置和清除路径、停止路径、元数据合并，以及渲染进程里 `streamReopen` 分支和 `BoundedIdSet.delete`。这说明这些分支还没有测试覆盖，是下一步要补的地方。这个脚本目前手动运行，不在 CI 里。

### 教训

修复前，相关的单元测试一直是绿的。原因是测试里构造的 Pi 事件是理想化的：快照和累积的 delta 严格一致，旧代码“优先读快照”在这种输入下没有任何问题。真实的 GLM 事件流一回放，问题就出来了。

流式管线这类代码，测试输入应该先从真实录制开始，再从录制里提炼构造器。手写的事件流只能证明代码符合我们对 SDK 的想象。

在 RongxinAI 仓库（Node 24）：

